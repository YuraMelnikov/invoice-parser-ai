# ADR-0004. Линковка позиций с ERP: гибридный матчер (артикул + вето + вектор)

- Дата: 2026-10-07
- Статус: принято

## Контекст

Задача 002: позиции накладных линкуются с кодами номенклатуры ERP
(справочник ~365 SKU) по наименованию. Наработки владельца
(`tmp/embeddings.json`, `tmp/erp.json`) покрывают только наполнение
векторных коллекций bge-m3 → Qdrant. Калибровка 2026-10-07
(`tmp/calibrate_linking.py`, `tmp/linking_matrix.md`) показала:

- все 23 эталонные позиции имеют score 0.43–0.60 к каталогу — их там нет
  (верные негативы);
- позитивный контроль: точные наименования ≥ 0.90, короткие ~0.71,
  неоднозначные обрывки ≤ 0.68;
- **критично:** bge-m3 не различает артикулы, отличающиеся одним знаком:
  «ДПП22-20.137.18.42» к «ДПП22-20.137.18.41» даёт score 0.9246,
  «ДПП23-…» — 0.9117. При чисто векторной линковке с T1=0.85 чужие модели
  улетали бы в учёт с неверным кодом.

## Решение

1. **Гибридный матчер** (`Invoice-006_Matcher`):
   - артикул (буквы+цифры с разделителями: ДПП22-20.137.18.41, ПВ3-10,
     PCAM_0744_000_114-102) извлекается и нормализуется (регистр,
     разделители, кириллические двойники → латиница);
   - артикулы с обеих сторон **совпали** → линковка, `link_method='article'`;
   - артикулы с обеих сторон **различаются** → **вето**: кандидат
     вычёркивается независимо от score (это другая модель);
   - артикула нет хотя бы с одной стороны → решает вектор,
     `link_method='vector'`.
   - Цифровые типоразмеры (14х1, 2050x1420x3) артикулами не считаются —
     их решает вектор (эвристика проверена на 13 контрольных примерах,
     `tmp/test_article.js`).
2. **Порог T1 = 0.85** (по калибровке: настоящие совпадения ≥ 0.90,
   мусор ≤ 0.68). Промах в «не слинковано» дешевле неверного кода;
   неслинкованное видно запросом из RUNBOOK §10.
3. **Свежесть справочника:** `Invoice-005_SKU-sync` каждый час делает
   полный рефреш коллекции `sku_catalog` (365 строк, кэш не нужен);
   устаревшие коды удаляются. Пустой ответ ERP прерывает тик — коллекция
   не затирается.
4. **Ключи Qdrant — детерминированные UUID v5:** позиции от
   `(file_name, line_no)` (переобработка файла перезаписывает те же точки,
   сирот нет), SKU от кода. Кэш `docs.item_embeddings` ключуется так же.
5. **Эмбеддинг позиций — отдельный `Invoice-004_Embeddings`** (не в
   Worker): сбой Qdrant/embed не должен ронять документ и обнулять
   ~10 мин распознавания (error-ветка Worker — backlog-задача 003).
6. **Результат — в `docs.invoice_items`:** `sku_code`, `link_score`,
   `link_method`, `link_processed` (флаг ставится всегда — и при успехе,
   и при «не найдено»; решение владельца). Очереди review нет.

## Последствия

- Остаточный риск: OCR ошибся в знаке артикула → вето → строка уходит в
  «не слинковано» (принято: промах виден, неверный код — нет).
- Артикульная эвристика эмпирическая; новый тип наименования, который она
  режет неправильно, → fixture в `tests/` и правка (стоп-правило AGENTS.md).
- При смене embedding-модели: полная переиндексация обеих коллекций и
  перекалибровка T1.
- Тик 006 идёт раз в 10 мин; первая линковка существующих 26 позиций
  произойдёт при активации workflow.

## Проверено

- Калибровка: `tmp/linking_matrix.md` (негативы), `tmp/calibrate_positive.py`
  (позитивы: точные ≥ 0.90, мусор ≤ 0.68).
- Эвристика артикула: `tmp/test_article.js` в node-контейнере n8n — 13/13
  контрольных примеров (совпадение при «-137.18 .41», вето на .42 и ДПП23,
  отсев типоразмеров).
- Миграция `sql/003_embeddings.sql` накатана, идемпотентна (двойной прогон).

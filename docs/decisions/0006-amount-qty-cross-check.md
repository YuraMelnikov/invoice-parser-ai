# ADR-0006. Контроль «стоимость / количество = цена»: поле amount и каскад коррекции количества

- Дата: 2026-10-08
- Статус: принято

## Контекст

ТТН-1 (Рейникс Системс → КАТЭК, `2216_фффффф.pdf`, 2026-10-08): модель
qwen3-vl:8b распознала количество «9,000» как 9000 вместо 9. Промт уже
содержит явное правило «запятая НИКОГДА не разделитель тысяч: „2,000“ — это 2»
(`extract_items_system.txt`, правило 4) — модель его проигнорировала. Ошибка
класса «десятичная запятая прочитана как разделитель тысяч» завышает
количество в 1000 раз (потенциально в 100/10) и не ловится ничем: позиции
уходят в матчер и ERP с завышенным qty.

На печатных формах (ТТН-1, УПД, ТН) у каждой позиции есть колонка
«Стоимость» (без НДС) = количество × цена. Проверено на этом документе:
равенство точное по всем 16 строкам, сумма колонки совпадает с «ИТОГО по
странице» (4 715,43), ×1,2 — с итогом «с НДС» (5 658,51). Арифметический
контроль надёжен.

## Решение (алгоритм — решение владельца 2026-10-08)

1. **Извлекаем и храним стоимость позиции** — поле `amount` (стоимость без
   НДС): в JSON-схему ответа VLM, промт, таблицу `docs.invoice_items`
   (миграция `sql/005_amount_qty_fix.sql`).
2. **Контроль в Code-узле «Parse & validate» воркера** после разбора ответа:
   если `amount / quantity` отклоняется от `price` не более чем на 10 % —
   оставляем как есть. Иначе последовательно пробуем `quantity / 1000`,
   `/ 100`, `/ 10` — берём **первый** делитель, при котором отклонение
   входит в 10 %. Если ни один не подошёл — **оставляем как есть**
   (без смены статуса документа и без error-ветки).
3. **Аудит правки** — колонка `qty_fix smallint` в `docs.invoice_items`:
   `1` — сошлось без правки; `1000/100/10` — исправлено этим делителем;
   `-1` — не сошлось ни с одним, оставлено как есть; `0` — проверка не
   выполнялась (qty/price/amount отсутствуют или нулевые). По `-1` и
   делителям ≠ 1 можно строить мониторинг качества.
4. **Eval зеркалит каскад**: `tests/run_eval.py` применяет тот же алгоритм
   к фактическому ответу модели перед сравнением с эталоном (иначе эталон
   с «правильным» количеством всегда расходился бы с сырым ответом модели).
   Допуск сравнения самого `amount` — как у прочих чисел (TOL).

## Последствия

- Схема `docs.invoice_items`: +2 колонки (`amount numeric(14,2)`,
  `qty_fix smallint NOT NULL DEFAULT 0`). Старые строки: `amount = NULL`,
  `qty_fix = 0` («не проверялось») — отличимы от новых.
- ERP-экспорт (ADR-0005) **не меняется**: схема `exportImport.dbo.invoice_items`
  заморожена; в ERP по-прежнему уходит исправленное `quantity` — этого
  достаточно, т.к. цель контроля — корректное количество.
- Матчер (ADR-0004) и переобработка изменений не требуют: worker пишет те же
  поля + 2 новых; триггер сброса `exported_at` работает как раньше.
- Каскад существует в двух реализациях (JS в воркере, Python в run_eval.py) —
  при смене алгоритма править обе; источник истины по алгоритму — эта ADR.
- Допуск 10 % шире копеечного округления цены: с запасом покрывает формы,
  где цена округлена, но не маскирует ошибку в 10+ раз.
- «Оставляем как есть» при несоответствии — осознанный компромисс владельца:
  документ не блокируется, аномалия видна по `qty_fix = -1`.

## Проверено

- Документ-инцидент стал fixture `tests/fixtures/test_05.pdf`
  (черновик эталона — на утверждении владельца).
- Каскад на фактическом ответе модели по этому документу: все 16 позиций
  исправляются делителем 1000 до точного равенства (см. задачу 005, DoD).

# ADR-0002. Пайплайн обработки: dispatcher → worker → archive

- Дата: 2026-10-06
- Статус: принято

## Контекст

На шаре `//192.168.1.30/m/Приходные накладные/AI` накапливаются PDF-сканы.
Нужна обработка потока файлов: регистрация, извлечение позиций vision-моделью,
вывод обработанных из входной папки. Обработка одного файла (рендер + VLM)
занимает минуты — синхронный цикл в одном workflow не подходит.

## Решение

Три независимых n8n-workflow (`workflows/`), связанных через очередь в
`docs.documents` (статусы new/processing/done/error):

1. **dispatcher** (тик 10 мин): регистрирует файлы шары (upsert), сбрасывает
   зависшие `processing` (>30 мин), захватывает батч до 8 файлов
   (`UPDATE ... WHERE status='new' RETURNING` — атомарно) и отправляет каждый
   в worker через webhook.
2. **worker** (webhook `nakladnye-worker`, Respond Immediately): render →
   qwen3-vl:8b (JSON-схема, только позиции) → валидация → `docs.invoices`
   (upsert, полный ответ в `raw_json`) + `docs.invoice_items`
   (delete+insert) → статус done; любая ошибка ветки → status error с
   `error_message`.
3. **archive** (тик 5 мин): `done` → `_archive/`, `error` → `_error/`,
   простановка `archived_at`.

Ключевые решения (утверждены владельцем 2026-10-06):

- **Стабильность файла.** В батч попадают только файлы с `file_mtime` старше
  3 минут (миграция 002): файл, ещё копирующийся на шару, не будет отдан
  воркеру на половине записи.
- **Error-файлы** выводятся из входной папки в `_error/` тем же archive-
  workflow, чтобы входная папка не зарастала и диспетчер не видел их вечно.
- **Коллизия имён в архиве**: если файл с таким именем уже есть в `_archive/`,
  новый получает префикс `YYYYMMDD-HHMMSS_` — архивный файл не затирается.
- **Перенос идемпотентен**: «src отсутствует, dst существует» = файл уже
  перенесён прошлым тиком — просто дозаписываем `archived_at`.

## Обоснование

- Очередь в Postgres (а не файловые флаги): атомарный захват, статусный
  аудит, восстановление после падения без внешних компонентов.
- Webhook fire-and-forget: диспетчер не блокируется на минуты обработки;
  воркер сам владеет финальным статусом.
- Только позиции в схеме ответа: шапка не хранится (решение владельца
  2026-10-05); полный ответ LLM остаётся в `raw_json`.

## Последствия

- Требуется миграция `sql/002_archived_at.sql` (`archived_at`, `file_mtime`).
- Креды Postgres (id `uSXpwajUhahtQd3N`) зашиты в экспортированных workflow;
  на другом инстансе n8n — привязать при импорте.
- Webhook воркера обязан быть в режиме Respond Immediately, иначе диспетчер
  словит таймаут, а файл через 30 мин уйдёт на повторную обработку
  (дубли компенсируются upsert/delete+insert, но это лишняя работа).
- Повторная обработка файла безопасна: invoices — upsert, items —
  delete+insert, перенос — идемпотентен.
